# DW-003: Customer KYC Specification

## Status

APPROVED FOR IMPLEMENTATION on `feature/customer-kyc`, targeting `develop`.

## Goal

Implement the Customer KYC bounded context required before wallet-account creation while preserving financial-platform security, privacy, auditability, Hexagonal boundaries, and the Keycloak authorization model established by DW-001/DW-002.

## Scope

DW-003 owns:

- one KYC profile per authenticated Keycloak subject;
- customer self-service read, draft update, and submission flows;
- operator review with verify/reject decisions;
- PostgreSQL persistence and append-only Liquibase migrations;
- sensitive identity-data minimization: raw government document numbers are never persisted, logged, cached, or emitted to Kafka;
- HMAC-SHA256 document fingerprinting with an environment-provided secret and persisted last-four display value;
- immutable status-transition rules and optimistic concurrency protection;
- stable KYC error codes and REST contracts;
- typed KYC status-change event payloads written through a transactional outbox boundary for later consumers such as Wallet Account;
- Keycloak permission/composite-role additions required for KYC;
- reuse of DW-002 effective permission/scope resolution rather than introducing a second IAM store;
- Docker Compose, Testcontainers, repository-quality, Maven/Spotless, and GitHub Actions verification for the new service.

DW-003 does not own:

- wallet account creation or wallet-account state;
- Ledger, Transfer, Funding/Payout, limits, fraud, settlement, or reconciliation behavior;
- OCR, face matching, liveness, AML/sanctions screening, document binary storage, or a third-party KYC vendor integration;
- automatic reverification/expiry workflows;
- a second user/credential/role database competing with Keycloak.

## Domain model

### CustomerKyc

Identity:

- `kycId`: opaque UUID generated by the KYC context;
- `userId`: immutable Keycloak subject and unique owner key;
- `scopePath`: immutable authorization scope captured when the profile is first created.

Profile fields:

- `legalName`;
- `dateOfBirth`;
- `nationality` as uppercase ISO-3166 alpha-2 code;
- `documentType`: `NATIONAL_ID` or `PASSPORT`;
- `documentFingerprint`: HMAC-SHA256 of the normalized document number, never returned by REST;
- `documentLast4`: last four normalized characters for safe self-service display;
- `documentCountry` as uppercase ISO-3166 alpha-2 code;
- `documentExpiresAt`;
- `addressLine1`;
- `city`;
- `country` as uppercase ISO-3166 alpha-2 code.

Lifecycle fields:

- `status`: `DRAFT`, `PENDING_REVIEW`, `VERIFIED`, `REJECTED`;
- `submittedAt`;
- `reviewedAt`;
- `reviewedBy`;
- `rejectionReasonCode`;
- `createdAt`;
- `updatedAt`;
- optimistic `version`.

### State machine

Allowed transitions:

```text
new profile -> DRAFT
DRAFT -> PENDING_REVIEW
REJECTED -> DRAFT when the customer changes the draft
PENDING_REVIEW -> VERIFIED
PENDING_REVIEW -> REJECTED
```

Rules:

- `VERIFIED` is terminal in DW-003;
- a customer cannot modify `PENDING_REVIEW` or `VERIFIED` data;
- changing a `REJECTED` profile clears the previous review metadata and returns it to `DRAFT`;
- only `DRAFT` can be submitted;
- only `PENDING_REVIEW` can be verified or rejected;
- rejection requires a stable non-blank `rejectionReasonCode`;
- a reviewer cannot review their own KYC profile;
- status timestamps are set by the application clock, never accepted from client input.

## Sensitive-data policy

The raw document number exists only in the incoming validated command and the fingerprint adapter call.

Persistence stores only:

- HMAC-SHA256 fingerprint;
- last four normalized characters.

The HMAC key comes from `KYC_DOCUMENT_HMAC_SECRET` and has no source-controlled default. Startup fails when the key is absent or blank.

Never place raw document numbers, full KYC request bodies, HMAC keys, fingerprints, or sensitive address fields in application logs, audit text, Kafka payloads, exception messages, or metrics labels.

## Public REST contracts

All endpoints require a valid Keycloak bearer token.

### Customer self-service

- `GET /api/v1/kyc/me`
  - permission: `kyc:self:read`;
  - returns `404 KYC_NOT_FOUND` when no profile exists.

- `PUT /api/v1/kyc/me/draft`
  - permission: `kyc:self:write`;
  - creates the owner profile on first call or updates an editable profile;
  - request contains the raw document number; response contains only `documentLast4`.

- `POST /api/v1/kyc/me/submit`
  - permission: `kyc:self:submit`;
  - transitions `DRAFT -> PENDING_REVIEW`.

### Operator review

- `GET /api/v1/kyc/reviews/{kycId}`
  - permission: `kyc:review`;
  - caller must have hierarchical scope for the target profile `scopePath`.

- `POST /api/v1/kyc/reviews/{kycId}/decision`
  - permission: `kyc:review`;
  - caller must have hierarchical scope for the target profile `scopePath`;
  - request decision is `VERIFY` or `REJECT`;
  - `REJECT` requires `rejectionReasonCode`.

REST responses use the existing platform `ApiResponse` envelope.

## Authorization integration

KYC must reuse DW-002 authorization truth:

- Keycloak remains source of truth for roles, permissions, and group scopes;
- KYC does not add IAM tables;
- KYC resolves the current user's effective permissions/scopes through `be-auth-api` self-service endpoints using the incoming bearer token;
- the request-scoped effective authorization snapshot is converted to platform `CurrentAuthorization`/`WalletAuthorization`;
- cache behavior remains owned by `be-auth-api`; KYC does not duplicate Redis authorization cache logic;
- dependency failure never becomes authorization success.

Required realm permissions:

- `permission:kyc:self:read`;
- `permission:kyc:self:write`;
- `permission:kyc:self:submit`;
- `permission:kyc:review`.

`role:wallet-user` includes the three self-service permissions. `role:kyc-reviewer` includes `permission:kyc:review`.

## Persistence model

KYC owns its tables and migrations.

### `customer_kyc`

Required constraints:

- primary key `kyc_id` UUID;
- unique `user_id`;
- unique `document_fingerprint`;
- non-null lifecycle/profile fields required by submitted records;
- `version` for optimistic locking;
- timestamps stored as UTC-capable `timestamptz`.

### `kyc_outbox_event`

Stores a local transactional outbox row in the same database transaction as each KYC status change.

Minimum fields:

- `event_id` UUID primary key;
- `aggregate_id` UUID KYC id;
- `event_type`;
- `payload` JSONB encoded only through platform `OutboxPayloadCodec`;
- `created_at` timestamptz;
- `published_at` nullable timestamptz;
- `attempt_count` integer.

DW-003 guarantees atomic outbox creation. A generic publisher/replay process may be added when a consuming feature requires live Kafka delivery; no direct in-transaction Kafka publish is allowed.

## Typed event contract

Payload:

```text
KycStatusChangedPayload(
  kycId,
  userId,
  previousStatus,
  currentStatus,
  changedAt
)
```

The payload intentionally excludes legal name, birth date, document information, address, rejection details, and authorization data.

Event type: `CUSTOMER_KYC_STATUS_CHANGED`.

## Error codes

KYC defines stable error codes with platform `ErrorCode` semantics:

- `KYC_NOT_FOUND` -> 404;
- `KYC_NOT_EDITABLE` -> 409;
- `KYC_NOT_SUBMITTABLE` -> 409;
- `KYC_NOT_REVIEWABLE` -> 409;
- `KYC_REJECTION_REASON_REQUIRED` -> 400;
- `KYC_SELF_REVIEW_FORBIDDEN` -> 403;
- `KYC_SCOPE_REQUIRED` -> 403;
- `KYC_AUTHORIZATION_UNAVAILABLE` -> 503;
- `KYC_DOCUMENT_ALREADY_EXISTS` -> 409.

Bean Validation handles request-shape errors through the existing platform validation path.

## Concurrency and transaction rules

- each write use case is one local database transaction;
- optimistic versioning prevents lost updates and duplicate review transitions;
- uniqueness constraints protect one profile per Keycloak subject and one document fingerprint;
- concurrent submissions/reviews must result in one valid state transition and a conflict for stale competitors;
- status transition and outbox insert are atomic;
- no network call occurs inside the database transaction except authorization resolution completed before entering the transactional application operation.

## Observability and audit

- inherit platform HTTP tracing/correlation and structured logging;
- do not manually propagate `traceparent`/`tracestate`;
- log only identifiers, actor id/type, action, status transition, outcome, and latency-safe metadata;
- never log the KYC draft request/body or sensitive values;
- review decision stores `reviewedBy` and timestamps for immutable business audit evidence.
