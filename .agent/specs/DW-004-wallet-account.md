# DW-004: Wallet Account Specification

## Status

APPROVED FOR IMPLEMENTATION on `feature/wallet-account`, targeting `develop`.

## Goal

Implement the Wallet Account bounded context that gives a KYC-verified customer a stable wallet identity for later Ledger, Balance, Transfer, Hold, Funding, Limits, and Fraud capabilities without implementing those capabilities early.

## Scope

DW-004 owns:

- one wallet account per authenticated Keycloak subject and currency;
- customer self-service wallet opening and read/list flows;
- KYC-verification gating through the DW-003 service contract;
- PostgreSQL persistence and append-only Liquibase migrations;
- stable wallet identity, ownership, currency, scope, lifecycle status, timestamps, and optimistic version metadata;
- stable wallet error codes and REST contracts;
- a typed `WALLET_ACCOUNT_CREATED` payload written through a local transactional outbox boundary;
- Keycloak permission/composite-role additions required for wallet self-service;
- Docker Compose, Testcontainers, repository-quality, Maven/Spotless, Dockerfile, and GitHub Actions verification for the new service.

DW-004 does not own:

- balance fields or balance mutation;
- double-entry Ledger journals or journal posting;
- Transfer, Hold/Capture/Reversal, Funding/Payout, Limits, Fraud, Reconciliation, Settlement, or Statement behavior;
- operator/admin wallet suspension/closure workflows, which may be introduced only when their owning feature defines the required business policy;
- a second user, credential, role, KYC, or authorization database;
- Redis as an authority for wallet existence or financial eligibility;
- direct in-transaction Kafka publication.

## Bounded context and deployment

Runnable service:

```text
backend/services/be-wallet-account-api
```

Package root:

```text
com.dnnthanh.wallet.be.walletaccount
```

Hexagonal flow:

```text
adapter/in/web
  -> application/port/in
  -> application/service
  -> domain
  -> application/port/out
  -> adapter/out/persistence
  -> PostgreSQL
```

KYC verification is an outbound cross-context port implemented with the existing DW-003 REST contract. Application/domain code must not depend on Spring Security, KYC REST DTOs, JPA entities, or adapter classes.

## Domain model

### WalletAccount

Identity and ownership:

- `walletId`: opaque UUID generated by Wallet Account;
- `userId`: immutable Keycloak subject;
- `scopePath`: immutable authorization scope copied from the verified KYC profile at wallet creation;
- `currency`: immutable uppercase ISO-4217 currency code.

Lifecycle:

- `status`: `ACTIVE` in DW-004;
- `createdAt`;
- `updatedAt`;
- optimistic `version` persisted for safe future lifecycle extensions.

Rules:

- a new wallet is always `ACTIVE`;
- the same `userId + currency` pair can exist only once;
- `walletId`, owner, scope, and currency are immutable;
- a wallet is not a balance and contains no available/current/ledger balance field;
- the supported-currency allow-list is environment/YAML-backed configuration and is validated before persistence;
- ISO currency normalization uses JDK currency semantics rather than a project-local currency helper.

## KYC prerequisite

Opening a wallet requires the current customer's DW-003 profile to be `VERIFIED`.

The Wallet Account service calls:

```text
GET /private/api/v1/kyc/me
```

with the incoming bearer token before starting the wallet database transaction.

Rules:

- `KYC_NOT_FOUND` or any non-`VERIFIED` status -> `WALLET_KYC_REQUIRED`;
- dependency timeout/unavailability/malformed response -> `WALLET_KYC_UNAVAILABLE`;
- returned `userId` must equal the current authenticated subject; mismatch fails closed as dependency/integrity failure;
- `scopePath` is captured from the verified KYC response and stored on the new wallet;
- Wallet Account never reads KYC tables directly;
- KYC network resolution must complete before the local PostgreSQL write transaction begins.

## Public REST contracts

All endpoints require a valid Keycloak bearer token and use the platform `ApiResponse` envelope.

### Open wallet

`POST /private/api/v1/wallets`

Permission: `WALLET_SELF_CREATE`.

Request:

```json
{
  "currency": "VND"
}
```

Behavior:

- normalize and validate the ISO currency code;
- reject currencies outside the configured supported set;
- require verified KYC;
- create one `ACTIVE` wallet for the current subject and currency;
- concurrent/successive duplicate creation maps to stable `WALLET_ALREADY_EXISTS`.

### List my wallets

`GET /private/api/v1/wallets/me`

Permission: `WALLET_SELF_READ`.

Returns only wallets owned by the authenticated subject, ordered deterministically by creation time then wallet id.

### Get my wallet

`GET /private/api/v1/wallets/{walletId}`

Permission: `WALLET_SELF_READ`.

Lookup is ownership-scoped. A wallet owned by another user is not disclosed and follows `WALLET_NOT_FOUND` semantics.

## Authorization integration

Keycloak remains the source of truth.

Required realm permissions:

- `permission:wallet:self:create` mapped to code `WALLET_SELF_CREATE`;
- `permission:wallet:self:read` mapped to code `WALLET_SELF_READ`.

`role:wallet-user` includes both permissions in addition to the existing KYC self-service permissions.

The Wallet Account context owns no IAM tables and does not duplicate the DW-002 Redis authorization cache.

## Persistence model

Wallet Account owns its database and migrations.

### `wallet_account`

Minimum columns and constraints:

- `wallet_id` UUID primary key;
- `user_id` non-null;
- `scope_path` non-null;
- `currency` non-null length 3;
- `status` non-null;
- `created_at` timestamptz non-null;
- `updated_at` timestamptz non-null;
- `version` bigint non-null;
- unique constraint on `(user_id, currency)`.

No balance, ledger amount, hold amount, transfer amount, or KYC document field is allowed in this table.

### `wallet_outbox_event`

Stores the account-created event in the same local transaction as the wallet row.

Minimum fields:

- `event_id` UUID primary key;
- `aggregate_id` UUID wallet id;
- `event_type`;
- `payload` JSONB encoded only through platform `OutboxPayloadCodec`;
- `created_at` timestamptz;
- `published_at` nullable timestamptz;
- `attempt_count` integer.

DW-004 guarantees atomic outbox creation only. A future publisher/replay capability may deliver it to Kafka; no direct Kafka send occurs in the wallet creation transaction.

## Typed event contract

Payload:

```text
WalletAccountCreatedPayload(
  walletId,
  userId,
  currency,
  status,
  createdAt
)
```

Event type: `WALLET_ACCOUNT_CREATED`.

The event intentionally excludes balance data, KYC profile/document data, bearer tokens, Keycloak roles, and authorization scopes.

## Error codes

- `WALLET_NOT_FOUND` -> 404;
- `WALLET_KYC_REQUIRED` -> 409;
- `WALLET_KYC_UNAVAILABLE` -> 503;
- `WALLET_UNSUPPORTED_CURRENCY` -> 400;
- `WALLET_ALREADY_EXISTS` -> 409.

Bean Validation handles request-shape errors through the existing platform validation path.

## Transaction and concurrency rules

- KYC network verification completes before the write transaction begins;
- wallet row + account-created outbox row are committed atomically in one local PostgreSQL transaction;
- the unique `(user_id, currency)` constraint is the final race-safety boundary;
- duplicate concurrent opens produce one persisted wallet and stable `WALLET_ALREADY_EXISTS` for the loser;
- no cross-context database access and no XA/distributed transaction;
- no direct Kafka publish inside the transaction.

## Observability and security

- inherit platform HTTP tracing, correlation, structured logging, and common error handling;
- do not manually propagate `traceparent`, `tracestate`, or synthetic trace ids;
- log only identifiers, currency, status, actor id/type, action, outcome, and latency-safe metadata;
- never log bearer tokens or the KYC response body;
- `correlationId` remains distinct from distributed trace context.

## Configuration

Service configuration is YAML/environment backed:

- datasource host/port/name/user/password;
- KYC base URL;
- supported currencies;
- Keycloak issuer/JWK URLs.

`WALLET_DB_PASSWORD` has no source-controlled secret value. Supported currencies are non-secret product configuration and may have a local/demo default of `VND`.
